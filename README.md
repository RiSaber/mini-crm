# Мини-CRM «Объекты и задачи»

Тестовое задание: CRM для строительной компании. Постановщик ставит задачи по объектам (стройкам), исполнители берут их в работу и отправляют на проверку.

**Стек:** React 19 + TypeScript, Vite, Supabase (Postgres, Auth, RLS). UI-библиотеки нет, стили в одном файле `src/index.css`.

## Где что лежит

| Путь | Что там |
|---|---|
| `supabase/migrations/` | вся схема базы, права доступа (RLS), проверка переходов статусов и история |
| `src/lib/status.ts` | подписи статусов и какие кнопки показывать (только интерфейс, правила дублируются в базе) |
| `src/pages/` | экраны: вход, объекты, карточка объекта, задачи, карточка задачи |
| `scripts/migrate.mjs` | применяет миграции к базе |
| `scripts/seed.mjs` | создаёт тестовых пользователей, объекты и задачи в разных статусах |
| `scripts/security-check.mjs` | проверяет защиту запросами напрямую в Supabase, в обход интерфейса |
| `docs/ОБЪЯСНЕНИЕ.md` | как устроена система, простыми словами |
| `docs/РЕШЕНИЯ.md` | решения и допущения там, где ТЗ неоднозначно, и что не сделано |

## Запуск

Нужны Node.js 20+ и проект в [Supabase](https://supabase.com) (бесплатного тарифа хватает).

1. Установить зависимости:
	```bash
	npm install
	```
2. Скопировать `.env.example` в `.env` и заполнить значения из Supabase (Project Settings → API и Database → Connection string).
	`SUPABASE_SERVICE_ROLE_KEY` и `DATABASE_URL` нужны только локальным скриптам. Во фронтенд они не попадают: Vite отдаёт в браузер только переменные с префиксом `VITE_`. Файл `.env` в `.gitignore`.
3. Применить миграции:
	```bash
	npm run db:migrate
	```
	Вместо этого можно по очереди выполнить файлы из `supabase/migrations/` в SQL Editor панели Supabase.
4. Отключить открытую регистрацию: Authentication → Sign In / Providers → выключить «Allow new users to sign up».
5. Создать тестовые данные (3 пользователя с паролем из `SEED_PASSWORD`, 3 объекта, 7 задач):
	```bash
	npm run db:seed
	```
6. Проверить защиту:
	```bash
	npm run test:security
	```
7. Запустить приложение:
	```bash
	npm run dev
	```

### Деплой на Vercel

Импортировать репозиторий, в Environment Variables добавить только `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Файл `vercel.json` перенаправляет все адреса на `index.html`, чтобы работали прямые ссылки на страницы.

### Пользователи

Регистрации нет, пользователей создаёт администратор: скриптом `seed.mjs` или в панели Supabase (Authentication → Add user). Профиль создаётся автоматически с ролью «исполнитель». Чтобы сделать пользователя постановщиком, выполнить в SQL Editor:

```sql
update public.profiles set role = 'manager' where email = 'user@example.com';
```

## Как устроена защита

- **RLS на всех таблицах.** Постановщик видит всё. Исполнитель видит только свои задачи, объекты с этими задачами и историю своих задач.
- **Права на колонки.** Через API у задачи можно менять только название, описание, объект и исполнителя (и только постановщику). Колонки статуса, автора и даты создания для API закрыты.
- **Смена статуса только через функцию `change_task_status`.** Она проверяет по таблице переходов, кто и из какого статуса может перевести задачу, требует комментарий при возврате на доработку и в той же транзакции пишет историю.
- **История только для чтения.** Писать в `task_history` могут только функции базы, поэтому через API её нельзя добавить, изменить или удалить.
- **Роль нельзя поднять себе самому.** Таблица `profiles` через API доступна только на чтение, роль при создании берётся из `app_metadata`, которую задаёт только администратор.
- **Служебные функции в схеме `private`**, которую Supabase не публикует в API.
- **Открытая регистрация выключена**, секретный ключ лежит только в локальном `.env`.

Проверки собраны в `npm run test:security`: скрипт входит под каждым пользователем и пытается сделать запрещённое напрямую через API.
