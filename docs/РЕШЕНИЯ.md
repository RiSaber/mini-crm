# Решения и допущения

Что я решил сам там, где ТЗ допускает разные варианты, и чего не успел.

## Роли и пользователи

- **Роль хранится в таблице `profiles`.** Профиль создаётся триггером при создании пользователя, по умолчанию роль «исполнитель». Постановщика назначает администратор: через `app_metadata` (Admin API) или SQL-запросом. Пользователь не может поменять роль сам: `profiles` через API доступна только на чтение, а `app_metadata` меняется только секретным ключом.
- **Найденная проблема.** Supabase Admin API записывает `app_metadata` вторым шагом, уже после создания строки пользователя, и при вставке роль не видна. Поэтому появилась вторая миграция: роль синхронизируется и при обновлении `app_metadata`.
- **Профили видят все вошедшие** (имя, email, роль). Без этого исполнитель не увидел бы в истории имя постановщика. Если email исполнителям показывать нельзя, можно оставить им только имя через отдельное представление (view).

## Объекты и задачи

- **Исполнитель обязателен при создании задачи.** ТЗ не говорит, может ли задача быть без исполнителя. Если исполнителя нет, переход «Новая → В работе» некому выполнить, поэтому поле обязательное.
- **Исполнителем может быть только пользователь с ролью «исполнитель»** (проверяет триггер в базе).
- **Постановщик может сменить исполнителя и объект в любом статусе.** Статус при этом не меняется. После переназначения прежний исполнитель перестаёт видеть задачу.
- **Объект нельзя удалить, пока в нём есть задачи.** Иначе одним нажатием можно потерять задачи вместе с историей. Сначала нужно удалить или перенести задачи.
- **Удаление задачи удаляет и её историю.** ТЗ разрешает постановщику удалять задачи и запрещает удалять историю через API. Я понял это так: отдельные записи истории удалить или подделать нельзя, но если удаляется сама задача, её история уходит вместе с ней. Если нужен журнал удалённых задач, лучше «мягкое» удаление (пометка в архиве) вместо настоящего.
- **Исполнитель в карточке объекта видит только свои задачи этого объекта**, а не все. Так я понял фразу «видит только свои задачи».
- **Принятая задача финальная.** Из «Принята» переходов нет: в ТЗ их нет, а «другие переходы запрещены».
- **Комментарий можно оставить при любом переходе**, обязателен он только при возврате на доработку.

## Безопасность

- **Статус меняется только через функцию базы `change_task_status`.** На колонки `status`, `author_id`, `created_at` у API нет прав записи (права на уровне колонок), поэтому прямой `UPDATE` статуса отклоняется даже у постановщика. Функция проверяет переход по таблице из ТЗ и в той же транзакции пишет историю. Строка задачи блокируется (`for update`), чтобы два одновременных нажатия не нарушили цепочку статусов.
- **Новая задача через API всегда создаётся в статусе «Новая»**, автор — тот, кто вошёл, дата — текущая. Это задаёт база, а не клиент.
- **Чужая задача выглядит как несуществующая.** На попытку сменить статус чужой задачи исполнитель получает «Задача не найдена», а не «нет прав», чтобы по ответу нельзя было проверить, существует ли задача.
- **Служебные функции и таблица миграций лежат в схеме `private`**, которую Supabase не публикует в API (это предложил Security Advisor).
- **Security Advisor:** ошибок нет. Осталось одно предупреждение: `change_task_status` с `SECURITY DEFINER` доступна вошедшим. Так задумано, это единственный способ сменить статус, права проверяются внутри функции. Ещё одно предупреждение — защита от утёкших паролей, она есть только на платном тарифе Supabase.
- **Ключи.** Во фронтенде только публичный ключ (publishable). Секретный ключ и пароль базы лежат в локальном `.env`, он в `.gitignore`.
- **Проверка в обход интерфейса** — скрипт `npm run test:security`: 22 попытки сделать запрещённое прямыми запросами к Supabase под разными пользователями и без входа. Все отклоняются.

## Интерфейс

- UI-библиотеку не брал: экранов мало, хватило одного CSS-файла. Вёрстка адаптивная, проверена на ширине 375 px.
- Кнопки действий считаются на клиенте по той же таблице переходов (`src/lib/status.ts`). Это только удобство: если клиент ошибётся или его подменят, база всё равно не пропустит запрещённое.
- Для постановщика страница «Мои задачи» превратилась во «Все задачи» с фильтром по статусу: по ней удобно находить задачи «На проверке».

## Что не успел или сознательно не делал

- Нет автотестов интерфейса. Безопасность покрыта скриптом проверок, сценарии интерфейса я прошёл вручную под тремя пользователями.
- Нет пагинации и поиска: для 2–3 объектов не нужны, при росте данных понадобятся.
- Нет обновления в реальном времени (Supabase Realtime): изменения другого пользователя видны после перехода по странице.
- Нет смены пароля и восстановления доступа: пользователей ведёт администратор.
- Типы базы описаны вручную, а не сгенерированы (`supabase gen types`).
